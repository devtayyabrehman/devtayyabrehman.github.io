Your Store Loads Quickly but Feels Slow: A Guide to INP

Learn how to investigate delayed taps and clicks using Interaction to Next Paint, field data, browser profiling, and focused fixes.

Tayyab Rehman

A page can appear quickly and still feel sluggish when a shopper opens a menu, changes a product variant, applies a filter, or adds an item to the cart. Interaction to Next Paint (INP) measures responsiveness across interactions during a visit, rather than measuring only the first visible content.

What INP tells you

INP observes interactions and reports a representative latency. A delay can come from time before event handlers begin, expensive JavaScript processing, or time waiting for the browser to present the next frame. web.dev defines a good INP as 200 milliseconds or less at the 75th percentile; examine mobile and desktop separately because their constraints differ.

Start with real-user evidence

Use field data to learn whether the issue affects many users and which page templates or devices are involved. A single slow interaction in a development build is a clue, not proof of a widespread problem. Ask which action is affected: opening the navigation, selecting a size, using search, submitting a form, or updating a cart.

If field data identifies an interaction, reproduce that exact action in browser developer tools. Record the page state and device conditions. Third-party scripts, large application bundles, and long main-thread tasks can contribute, but the profile should identify the work rather than assumptions about a particular plugin.

Separate the interaction into three questions: was the browser already busy before the event handler could start; did the handler itself do too much synchronous work; or did the browser take too long to present the next frame afterward? The Performance panel's interaction track and main-thread activity help distinguish those cases. A long task from a tag manager that began before the click calls for a different fix from an expensive product-filter calculation inside the click handler.

Write down one reproducible test case before changing code: page template, device profile, starting state, exact action, and expected result. For a filter, that might be “open the sale category on a mid-range Android profile, choose a size, and wait for the results and active-filter label.” Repeat the same path after a change so a visual improvement is not mistaken for a faster but broken control.

Profile the action, not just the page load

Use the Performance panel to record a click or tap through the next visual update. Inspect long tasks, scripting, style recalculation, layout, and rendering. Look for event handlers that parse or filter large data sets synchronously, rerender a broad component tree, or trigger repeated layout reads and writes.

Try to reproduce the specific slow action while the page is in the state where it occurs. For example, a product filter may be responsive with one result but stall when it needs to process a large catalog. Record the interaction, inspect the event timing, and find which work occupies the main thread. If a delay happens before the handler begins, investigate other scripts already running; if it occurs after the handler, inspect the work and rendering it triggered.

Make the interaction cheaper

  • Keep event handlers focused and avoid synchronous work that can be deferred.
  • Reduce unnecessary React rerenders by fixing state boundaries and unstable dependencies.
  • Split or defer nonessential JavaScript, especially on pages where it is not used.
  • Break up long tasks and ensure visual feedback appears promptly.
  • Test third-party scripts and extensions individually before removing functionality.

Do not add debouncing everywhere: it may make a control feel less responsive or delay essential feedback. Match the change to the interaction and verify that keyboard, touch, and assistive-technology users still get a clear response.

For a large React view, first identify which state update causes unrelated components to render. Move state closer to the part of the interface that needs it where practical, avoid recalculating large lists during every keystroke, and consider rendering only visible results for very long lists. Use a web worker for genuinely CPU-heavy work when appropriate, but remember that communication and data copying also have a cost. Profile again after each change.

Match the optimization to the phase you observed:

  • Input delay: Find the task already occupying the main thread when the shopper taps. Reduce unnecessary startup work, split a long task, or defer work that is not needed for the current view. Do not assume the click handler caused a delay that began before it ran.
  • Processing time: Narrow the handler's responsibility. Avoid parsing a large response, recalculating every product, or updating unrelated components synchronously. If computation must continue, provide clear progress feedback and verify that the final state is correct.
  • Presentation delay: Inspect style recalculation, layout, and paint after the handler. Avoid repeated layout reads mixed with writes, and check whether a large region is being redrawn for a small state change.

For a search field, measure both typing and the moment results update. A delay after every keystroke may indicate repeated filtering, while a pause before typing is accepted may point to other main-thread activity. For add-to-cart, check whether the cart count, confirmation, and accessible status message all update together. A fast animation alone does not prove the underlying action finished.

Avoid changing several scripts and components at once. If the next test improves, you will not know which change helped; if another interaction breaks, the rollback becomes harder to reason about. Keep the change small, preserve a clear before-and-after trace, and rerun the same scenario before moving to a different bottleneck.

When comparing field results, look at the same page type and device segment over a suitable reporting period. Changes in traffic mix, promotions, or a seasonal product launch can change which interactions visitors perform. A median value can conceal a small group of very slow interactions; Core Web Vitals evaluations commonly focus on the 75th percentile, so keep that percentile and the device grouping visible in your report.

Do not collect more personal interaction data than the investigation needs. A performance trace may include page text, query values, or account-specific details. Use test accounts for sensitive flows, redact recordings before sharing, and follow the site's consent and retention rules for any real-user monitoring. Performance work should not quietly become unnecessary collection of customer behavior.

The practical outcome is a repeatable before-and-after record: the action, the observed delay phase, the change made, the result, and any accessibility or functional regression checks. If the improvement appears only in a synthetic run, keep investigating rather than promising every shopper will experience the same change. Field data can take time to reflect a deployment, and a small site may not have enough observations for a strong statistical claim.

Verify after shipping

Keep the test scenario realistic: use a representative catalog size, a logged-in state when relevant, and the same device class where the issue was observed. Check both the visual response and whether the action completed correctly. A control that appears instant but fails to update the cart or announce its state accessibly is not an improvement. Revisit field data after enough real visits have accumulated to make a useful comparison.

Retest the same interaction in a production-like build, then watch field data after release. The web.dev INP guide breaks latency into actionable phases. The key is to optimize the slow user action, not chase an abstract score disconnected from how the site is used.

For a page where the initial display is slow too, use the separate WooCommerce LCP investigation guide; load speed and interaction responsiveness require different evidence. If repeated Effects trigger expensive updates in a React storefront, the React Effect debugging guide helps trace that narrower cause.

INP questions store teams ask

Does a good lab score prove every shopper has a responsive store?

No. A lab run is a controlled sample; field data reflects real devices, networks, and visits. Use the lab to reproduce and explain an issue, then check field data after shipping.

Should I delay every third-party script?

No. First confirm the script contributes to the slow interaction. Delaying analytics, consent, payment, or support code without checking dependencies can break measurement or important behavior.

Is debouncing a search or filter always a fix?

No. Debouncing reduces how often work starts during rapid input, but it also adds wait time. Choose a delay only when profiling shows repeated work is the cause, and verify that keyboard and assistive-technology users receive clear updates.

What should I compare after a change?

Repeat the same action with the same route, device class, data volume, and starting state. Check that the control still works, then compare field results once enough visits have been collected.
